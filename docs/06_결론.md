# 8단계 · 결론과 회고

작성일: 2026-11-18

## 결론 한 문장
> **합성 시험용 명세서 20장에서는 후보 A(PP-OCRv5 한국어 + 규칙 파싱, 노트북 CPU)가 성공 기준 6개를 모두 넘었다. 구축을 결정하려면 실제 명세서 5~10장(거래처명·단가 가림)으로 같은 채점기를 다시 돌려야 한다.**

## 판정

| 후보 | 판정 | 근거 |
|---|---|---|
| A. PP-OCRv5 한국어 + 규칙 파싱 | **다음 단계(실제 서류 재측정) 진행** | 기준 1~6 통과. 조용한 오류 0, 장당 16.7초 (17번 결함 수정 후 재측정 포함) |
| B. PaddleOCR-VL 1.6 | **이 노트북에서는 쓰지 않음** | 기준 1·4·5·6 미달. 장당 174.5초(CPU), 표 구조 불안정(20장 중 4장), 신뢰도·줄 위치 없음 |
| C. Qwen3-VL-2B | **판단 못 함** | 설치·다운로드를 허락하지 않아 시도하지 않음 |
| 기준선: 직원 수기 입력 | **판단 못 함** | 현행 수준 미측정. A가 사람보다 나은지는 이 PoC로 말할 수 없다 |

- **AI는 엑셀 행 초안만 만들고 반영은 사람이 확인 후 한다**는 설계(0단계)는 그대로 유지한다. 조용한 오류 0은 합성 샘플 20장에서의 값일 뿐이다.

## 결론에 반드시 같이 남길 제약
1. **현행 수준 미측정.** 성공 기준의 숫자는 노트북 예시(100개 중 3개)를 빌렸고 처리 시간 60초는 잠정값이다. A가 직원보다 빠르거나 정확한지는 모른다.
2. **합성 샘플만으로 쟀다.** 실제 서류의 번짐, 인쇄 불량, 거래처별 양식 차이가 빠져 있다.
3. **A의 파서는 양식 3종의 모양을 개발 중에 봤다.** 내용(숫자, 품목)은 다른 시드로 만든 개발용 샘플로만 맞췄지만, 거래처가 다른 양식을 보내면 파서를 다시 손봐야 한다.
4. **후보가 Paddle 계열 둘뿐이다.** 범용 모델(C)과의 비교가 빠졌다.
5. **GPU를 쓰지 않았다.** paddlepaddle이 CPU 빌드였다. B가 느린 이유의 상당 부분이 이것이며, GPU 빌드에서 B의 시간은 달라질 수 있다. 다만 B의 신뢰도·위치·표 구조 문제는 실행 장치와 무관하다.
6. **네트워크 차단은 파이썬 소켓까지만 확인했다.**
7. **기준 5(위치)는 형식만 채점했다.** 기울어진 스캔에서 A의 박스가 옆 줄까지 덮는 것을 그림으로 확인했다(`04_오류분석.md`).
8. **손글씨 정정은 고친 샘플 한 장으로만 확인했다.** 17번의 줄 그은 인쇄 금액이 잘못 찍힌 결함(`70,000`, 맞는 값은 `28,000`)을 발견해 17번만 고쳐 A를 다시 쟀고, 결과는 같았다(조용한 오류 0). 하지만 A가 정정을 이해한 것이 아니라, 취소선 글자의 신뢰도가 0.90 밑으로 떨어지고 손글씨가 어긋난 줄로 읽혀 확인 필요가 붙은 것이다. 손글씨가 선명하거나 취소선이 얇으면 조용히 통과할 수 있고, 한 장으로는 알 수 없다. 결함을 처음 발견했을 때 "의도대로였다면 조용히 통과했을 가능성이 크다"고 추정했는데 이 샘플에서는 틀렸다.

## 실제 서류로 다시 잴 때 할 일 (구축 결정 전)
1. 실제 명세서 5~10장을 모은다. 거래처마다 1장 이상, 손글씨 정정이나 흐린 팩스가 있는 것 2~3장을 넣는다.
2. 거래처명·단가를 가리지 않고 쓸 수 있는지 먼저 정한다. 가린다면 가린 칸은 채점에서 뺀다.
3. **모델을 돌리기 전에** 정답을 손으로 입력해 `정답.json` 형식으로 저장한다.
4. 같은 날 직원이 같은 서류를 입력하는 시간과 오류 수를 잰다(제약 1 해소).
5. `src/run_a.py`와 `src/score.py`를 **고치지 않고** 돌린다. 양식이 달라 파서가 무너지면 그 자체를 결과로 적는다.

## 기준 밖에서 고칠 것 (다음 PoC 후보)
- **확인 필요 비율 낮추기**: 맞는 값에 붙은 확인 필요가 14개였다. 과거 명세서의 품목 목록(품목 마스터)과 대조하면 `깨잎`, `소급창` 같은 오독을 고치거나 확인 필요를 줄일 수 있다. 실제 기록이 생긴 뒤에 할 일이다.
- **기울어진 스캔**: 박스를 네 꼭짓점으로 남기거나, 읽기 전에 스캔을 바로 세운다.
- **손글씨 정정**: 취소선(가로줄)을 검출해 그 줄을 무조건 확인 필요로 넘긴다. 지금은 우연히 걸렸다.
- **신뢰도 임계값 0.90**: 개발용에서 0.92로 틀린 사례가 있었다. 실제 서류로 다시 정한다.
- **라이선스**: 제품에 넣어 배포하려면 PyMuPDF(AGPL)를 상용 라이선스로 사거나 `pypdfium2`로 바꾼다(교체 전 라이선스 확인).

## 오늘의 회고 (초안 — 본인 생각으로 고쳐 쓰기)

**1. 적은 세 지점 중에서 고른 것과 뺀 것의 차이는 무엇이었습니까?**
- 후보는 명세서 엑셀 전사(입력과 전사), 고객 문의 답변 초안(검색의 변형), 카톡 발주 정리(분류와 배분 + 전사)였다.
- 명세서를 고른 이유는 **판정 기록이 없어도 정답을 서류에서 바로 만들 수 있기** 때문이다. 단가·거래처명이 있어 실행 위치 걸러내기도 실제 조건이 됐고, 노트북 예시 1·2와 유형이 겹치지 않았다.
- 고객 문의는 예시 1(사진 검색기)과 구조가 거의 같고, 답변 문장을 숫자로 채점하기 어렵고, 알레르기 답변은 틀렸을 때 되돌릴 수 없어 뺐다. 카톡 발주는 거래처마다 말투가 달라 기준을 세울 자료가 부족했다.

**2. 성공 기준의 숫자를 어디서 가져왔습니까? 현행 수준을 실제로 재 보았습니까?**
- **재 보지 않았다.** 품목 오류 3개 이하는 노트북 표의 예시를 빌렸고, 처리 시간 60초는 "사람이 한 장 입력하는 시간보다 확실히 짧을 만한 값"으로 잠정 정했다.
- 그래서 A가 기준을 넘었다는 것이 "직원보다 낫다"는 뜻은 아니다. 실제 서류로 다시 잴 때 직원의 시간과 오류를 같이 재야 한다.
- 대신 "조용한 오류"만 세고, 전부 확인 필요로 넘기는 꼼수는 비율 상한(20%)으로 막는 식으로 기준을 업무(틀린 금액이 정산에 그대로 들어가는 것)에 맞췄다.

**3. 실행 위치나 라이선스 때문에 제외한 후보가 있었습니까? 그 후보가 점수로는 몇 위였습니까?**
- 라이선스로 뺀 것: Qwen2.5-VL-3B(연구용 조건), VARCO-VISION-2.0(비상업, 한국어 특화).
- 사양으로 뺀 것: Qwen2.5-VL-7B(가중치 약 16.6GB).
- 실행 위치로 뺀 것: 외부 OCR·LLM API(실제 서류 반출 불가 가정).
- **이 후보들은 돌리지 않아 점수 순위가 없다.** 한국어 특화인 VARCO가 가장 정확했을 수도 있다. 조건으로 먼저 걸러냈기 때문에 "쓸 수 없는 후보가 1위가 되는" 일은 생기지 않았다.
- 별개로, 후보 C(Qwen3-VL-2B)는 라이선스·위치 조건은 통과했지만 설치 용량 때문에 내가 시도하지 않기로 했다. 그래서 범용 모델과의 비교가 빠졌다.

**4. 기준을 넘지 못한 항목이 있다면, 다음에 무엇을 바꿔 다시 확인하겠습니까?**
- B는 기준 1·4·5·6을 못 넘었다. 시간은 GPU 빌드 paddle로 다시 재 볼 수 있지만, 신뢰도와 줄 위치가 없는 것은 모델의 결과 형태라 바뀌지 않는다. **이 업무에서는 정확도보다 결과의 형태(박스와 신뢰도)가 중요했다.**
- A는 모두 넘었지만 합성 샘플에서의 결과다. 다음에는 **실제 명세서 5~10장과 직원 입력 시간**으로 같은 채점기를 고치지 않고 돌린다.
- 파서를 개발용 5장만 보고 고친 B가 시험용에서 처음 보는 표 모양(빈 칸 추가)에 무너졌다. 다음에는 개발용 샘플을 더 다양하게(양식당 여러 장) 쓴다.
